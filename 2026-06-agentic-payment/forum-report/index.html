Agentic Payments
真正要解决什么

不是让模型“能付款”，而是让 Agent 在明确授权、预算和责任边界内花钱，并且每一步都能解释、追踪和补救。

管理层一句话

稳定币是一条有条件优势的结算轨道；真正的产品机会，是 Agent 花钱前后的 授权 · 控制 · 凭证 · 对账 · 恢复。

依据三场共 90 分钟论坛精修转录与一份 68 页白皮书的页码化笔记。原始 WAV 与 PDF 当前不在本地原路径，因此本文不把发言、市场数字或协议状态包装成已核事实。

01 · WHAT

可证明的委托

系统要证明谁允许 Agent，在什么任务、金额、对象和期限内行动。

02 · RAIL

稳定币是选项

跨境和机器原生更适配；本地受理、退款与责任仍要靠完整支付体系。

03 · WEDGE

B2B / API 先行

规则明确、可计量、可限制预算，比开放式 C 端代购更容易验证。

04 · NEXT

90 天受控试点

先做控制层，用同一真实负载比较余额、卡与稳定币，不先造新轨道。

01 · Definition

这到底是什么

传统支付只需判断“能否扣款”。Agentic Payments 还必须回答：这笔钱为什么可以被 Agent 花掉？

一个企业场景
“比较三家模型 API；在本月 5 万元预算内买最合适的套餐。价格上涨超过 10%，先找我确认。”
这是不是员工真实提出的任务？
Agent 是否有权代表公司购买？
供应商、用途与金额是否合规？
买错、未交付或重复扣款怎么办？

完整流程不是“Agent → 钱包”

STEP 01
支付意图为什么买、买什么、服务哪个任务
STEP 02
授权谁允许、额度、对象、期限与撤销
STEP 03
政策与风险预算、供应商、欺诈与合规检查
STEP 04
多轨执行卡、银行、余额、发票或稳定币
STEP 05
结算最终性、费用、FX 与流动性
STEP 06
凭证与恢复交付、对账、退款、争议与审计
核心对象：Payment Intent。 它把原始任务与付款主体、供应商、金额、用途、期限和审批规则绑定起来，让金融执行不必直接相信模型。
02 · Forum

三场会议，各自补上哪块拼图

一场讲安全，一场讲成本，一场讲产品与市场。三者最后收敛到同一个问题：授权和责任。

14:13 · 安全与合规

钱在链上，不等于安全

托管有密钥风险或对手方风险；智能合约容易盲签；地址风险会变化；稳定币还可能被冻结。

产品含义：授权与风险检查必须在付款前内联，不能只留事后日志。
14:30 · 单位经济

机器支付先算清成本

小额高频交易难以承受高固定处理费。API、模型和数据消费比普通零售更像早期场景。

产品含义：逐请求计量，不必逐请求外部结算。
14:57 · PMF 与投资

最稀缺的是授权凭证

企业需要管理 Agent 的消费权限和错误责任；市场仍早，尚未出现公认 PMF，B2B 比 C 端更 ready。

产品含义：先做窄场景试点，不用“2027 爆发”替代需求证据。
03 · Stablecoin

稳定币：什么时候有用，什么时候不是答案

稳定币改善的是某些结算条件，不会自动补齐完整支付产品。

它擅长

  • 跨境和 24/7 结算
  • API 原生、可编程资金移动
  • 已经在链上的机器间支付
  • 低额高频场景的聚合后结算

它不自动解决

  • 用户授权、商户受理与责任
  • 退款、拒付、错误购买与未交付
  • 法币出入金、FX、税务和财务集成
  • 冻结、脱锚、链或桥故障后的恢复
稳定币场景适配判断
场景适配度为什么真正门槛
跨境 B2B / payout高，有条件24/7、共享状态、可编程牌照、FX、本地出金、冻结
API / 模型 / 数据消费中高适合程序化和聚合结算亚美分端到端成本与供应商接受度
链上 Agent-to-Agent高减少资产和轨道转换服务交付证明、重放与合约风险
国内本地零售低到中现有卡、钱包和银行更成熟商户覆盖、消费者保护、监管
开放式 C 端代购低到中错误购买与退款要求高MoR、拒付、责任和用户信任
最终判断：multi-rail，而不是 stablecoin-only。 Agent 应根据受理、成本、地域、风险和恢复要求，在卡、银行、余额、发票与稳定币之间选择。
04 · Unit economics

每次调用计费，不等于每次调用都结算

机器服务需要逐次知道“用了什么、多少钱、是否获授权”；资金却可以按阈值、时间窗口或净额批量移动。

10,000×
逐请求计量

每次模型/API 调用记录价格、用量、授权与交付凭证。

1 ledger
内部余额扣记

请求成功后更新企业余额或应付账，不立即触发外部资金移动。

1×
聚合外部结算

达到金额或时间阈值后，通过卡、银行或稳定币完成一次结算。

这样既能缩短服务商的信用周期，也不会让一万次调用承担一万次完整支付成本。真正要比较的是端到端成本：支付费、风险检查、流动性、失败、退款和对账，而不只是 gas。

05 · Market wedge

从哪里切入，验证速度最快

排序依据不是想象中的总市场，而是需求是否明确、边界能否控制、价值能否测量。

企业 API、模型、数据与工具消费

统一多供应商预算、逐次计量、降低应收风险并自动对账。

现在验证

规则明确的企业 Agent 费用

白名单供应商、低额度、明确用途；越界时再找人审批。

现在验证

跨境 B2B 供应商付款

验证更快结算与费用透明能否覆盖出入金、流动性和合规成本。

条件验证

开放式 C 端购物与旅行

受理、错误购买、退款、拒付和消费者保护最复杂。

暂不优先
06 · Product thesis

对公司的产品建议

Recommended position

先做 Agent Spend Control Layer
再决定是否承接完整责任

先帮助企业回答“这笔 Agent 支出为什么可以发生”，再逐步解决“发生错误后由谁赔”。这与团队已有的“责任层”方向一致，但把第一步收窄到可软件化、可试点的授权、凭证与对账。

01
授权

谁允许哪个 Agent，在什么范围、额度和期限内花钱。

02
政策

供应商、用途、地域、时间、频率和升级审批规则。

03
执行

按场景选择卡、银行、余额、发票或稳定币。

04
凭证

连接原始任务、报价、服务交付和支付结果。

05
对账

把每次使用、内部账和外部结算准确对上。

06
恢复

重复扣款、未交付或异常时暂停、退款和人工接管。

不要在第一阶段轻易承诺“我们赔”。 Merchant of Record、保证金、保险或赔付意味着资本、牌照、定价与风险承保。先证明企业愿意为控制层付费，再决定责任层做多重。
07 · 90-day plan

90 天行动方案

目标不是完成一个“通用支付网络”，而是用真实资金流推翻或证实产品假设。

WEEK 1–2

选窄场景

在多模型/API 费用控制与跨境 B2B payout 中选一个，记录客户当前审批、信用和月结流程。

WEEK 3–6

做最小控制层

实现 Intent、Mandate、Policy、Execution、Receipt 与 Dispute 六个对象。

WEEK 7–10

同负载比轨道

至少比较余额、虚拟卡、稳定币中的两种，测完整成本与失败恢复。

WEEK 11–13

受控生产试点

白名单、低额度、短期授权、人工接管；用真实资金验证。

08 · Decision metrics

公司应该看哪些指标

不要用协议发布数、测试网交易数或市场预测判断成败。

客户价值

WTP · 审批时间 · 自动完成率 · 月结工时

风险

越权支出 · 重复扣款 · 退款率 · 争议定位时间

单位经济

每请求收入 · 完整支付成本 · 流动性 · 人工成本

可靠性

成功率 · P95/P99 延迟 · 重试重复 · 恢复时间

商业

集成周期 · 重复付费 · 留存 · 毛利 · 销售周期

推翻条件

客户不单独付费，或现有 OAuth + 虚拟卡已足够

09 · Evidence gaps

现在还不能下结论的事

这些说法在录音或白皮书中出现过，但没有被本轮独立验证。

市场时点：“2027 年爆发”没有生产采用定义。
市场数字：稳定币增速、支付占比、卡费和损失金额。
协议能力：x402、AP2 等当前是否达到生产要求。
监管责任：不同地区的牌照、MoR、KYC/KYB 与报告主体。
真实经济性：亚美分支付的完整毛利、失败和对账成本。
PMF：哪家公司已经获得可持续客户留存和毛利。

Final takeaway

现在最值得验证的，不是哪条链，
而是企业是否愿意为 “让 Agent 安全地花钱” 付费。

如果控制层不能降低审批、风险或对账成本，Agentic Payments 就只是新的接口叙事；如果它能，结算轨道才是下一步优化问题。
